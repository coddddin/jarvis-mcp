# 파일 정리 — 미리보기·백업·이동·되돌리기

[문서 안내](../README.md) · [현재 계획](../PLAN.md)

## 이번에 묶어 구현한 도구

- `preview_file_organization(project)`: 프로젝트 최상위 파일의 분류·이동 계획.
- `apply_file_organization(preview_id)`: 백업 후 검토한 계획 적용.
- `list_file_organization_operations()`: 실행 내역·미완료 복구 작업 조회.
- `preview_file_organization_undo(operation_id)`: 기존 위치로 되돌릴 계획 확인.
- `undo_file_organization(preview_id)`: 새 백업 후 되돌리기.
- `preview_downloads_organization()`: 운영자가 허용한 다운로드 폴더의 읽기 전용 메타데이터 시뮬레이션.

각 도구는 `jarvis/features/files/tools/`의 독립 파일에 있으며 `jarvis/features/files/service.py` 서비스와 공유 가드레일·스냅샷 서비스를 사용합니다. 파일 정리 도입 시 6개를 추가했고 기존 12개를 유지했습니다. 현재 전체 목록은 [플러그인 안내](plugins.md)를 따릅니다.

## 프로젝트 정리 사용 순서

실제 이동·되돌리기는 Windows의 `JarvisWorkspace/projects/<프로젝트명>` 안에서만 지원합니다. 서버 코드·일반 다운로드 폴더·외부 경로에 쓰기 권한을 추가하지 않습니다.

1. 해당 데이터 영역에 정리할 프로젝트를 준비합니다.
2. Codex에서 자비스 서버를 재연결해 새 도구를 불러옵니다. 보이지 않으면 앱을 재시작합니다.
3. `preview_file_organization(project="projects/demo")` 결과에서 파일별 목적지·충돌·제외 항목을 확인합니다.
4. 실제 파일 정리를 사용자가 요청·승인한 범위에서 반환된 preview_id로 `apply_file_organization`을 호출합니다.
5. 반환된 operation_id와 backup_id를 보관합니다. 원래 위치로 되돌릴 때는 해당 operation_id로 undo 미리보기를 먼저 확인한 뒤 undo용 preview_id를 적용합니다.

미리보기는 10분 동안 한 번 사용하며 서버 재시작 후에는 새로 만들어야 합니다. 실행 내역은 저장되므로 재시작 후에도 새로운 undo 미리보기를 만들 수 있습니다. preview_id는 검토 상태를 연결하는 수단이며 사용자 신원을 인증하는 별도 승인 시스템은 아닙니다.

## 분류 범위

- 프로젝트 최상위의 문서·스프레드시트·이미지·음악·영상·압축·설치 파일을 확장자로 분류합니다. 하위 폴더 파일은 이동하지 않습니다.
- 목적지는 `Organized/<분류>/<UTC 수정월 YYYY-MM>/<기존 파일명>`입니다. 파일명은 바꾸지 않고 생성일·내용 기반 추론은 아직 사용하지 않습니다.
- 코드·알 수 없는 확장자·진행 중 다운로드·README·라이선스·requirements·에이전트 지침 및 비밀정보 후보는 이동 대상에서 제외합니다. 숨김 파일 등 기존 스냅샷 제외 정책도 따릅니다.
- ‘최종’, ‘복사본’, copy, 숫자 괄호 표시는 검토용 표시일 뿐 중복이라는 증거가 아닙니다. 자동 중복 삭제·내용 기반 이름 변경은 하지 않습니다.
- 대상 경로가 하나라도 충돌하면 전체 적용을 거부합니다. 충돌을 해결한 후 새 미리보기를 만듭니다. 기존 파일은 덮어쓰지 않습니다.
- SHA-256·크기·수정시각을 다시 확인해 미리보기 후 변경된 파일을 이동하지 않습니다. undo도 현재 위치의 파일이 바뀌거나 원래 경로가 다시 사용 중이면 거부합니다.

## 백업·롤백·기록

- 적용과 undo 모두 직전에 스냅샷을 생성합니다. 기존 스냅샷의 파일 크기·개수·보관 개수 상한을 그대로 사용하므로 미리보기 및 백업은 하위 폴더를 포함한 프로젝트를 읽고 해시 계산할 수 있습니다.
- Windows의 덮어쓰기 없는 동일 볼륨 rename을 사용합니다. 다른 운영체제는 이동을 거부하며 복사 후 삭제로 임의 대체하지 않습니다.
- 중간 실패·중단은 이미 이동한 파일을 역순으로 되돌립니다. 롤백 실패 시 후속 변경을 막고 operation_id를 보고합니다. 빈 분류 폴더가 남을 수 있습니다.
- `.jarvis-organization/<operation_id>.json`에 계획·백업 ID·상태·적용 내역을 보관합니다. 최대 100개이며 자동 삭제하지 않습니다. 기록은 엄격한 Pydantic 모델과 경로 규칙으로 재검증합니다.
- 적용 중 프로세스 강제 종료 등으로 `applying`, `undoing`, `rollback_failed`, `undo_rollback_failed`가 남으면 운영자 검토가 필요합니다. 현재 자동 장애 복구 도구는 없으며 journal을 확인 없이 지워 우회하지 않습니다.
- undo 실패의 롤백이 성공하면 `undo_rolled_back`이 되며 새 undo 미리보기로 다시 시도할 수 있습니다. 정리 적용 실패가 롤백된 작업은 새 적용 미리보기를 만듭니다.
- 스냅샷 복원은 병합 복원이므로 파일 정리의 되돌리기와 다릅니다. 이동 전 스냅샷을 무조건 복원하면 이동 후 파일이 추가로 남을 수 있습니다. 파일 정리 undo를 우선 사용하세요.
- 한 서버 안의 정리·스냅샷 작업은 공유 잠금으로 직렬화합니다. 여러 서버 프로세스·외부 프로그램의 동시 파일 변경을 완전히 격리하지 않으므로 쓰기 작업 중에는 다른 변경을 멈추세요. OS 수준 샌드박스·프로젝트 전체 트랜잭션은 아닙니다.

## 다운로드 폴더 미리보기

다운로드 읽기는 기존 프로젝트 경로 가드레일을 넓히지 않는 별도 읽기 전용 기능입니다. 코드 기본값은 비활성화이며 **MCP 서버 실행 환경에 `JARVIS_DOWNLOADS_READONLY=1`이 필요합니다.** 2026-10-17 사용자 요청으로 현재 PC의 Codex 자비스 등록 환경에 이 값을 저장하고 실제 MCP 스캔을 확인했습니다. 기존 연결은 재연결/앱 재시작 후 새 설정을 사용합니다. 당시 파일 20개를 확인했고 파일 이름 포함 결과는 Git에서 제외되는 `JarvisWorkspace/.jarvis-setup/downloads-preview.json`에 보관했습니다.

- Windows의 Downloads Known Folder 설정으로 경로를 확인합니다. 도구에 임의 경로를 넘길 수 없습니다. 네트워크·링크·정션 루트는 거부합니다.
- 최상위 파일 이름·확장자·크기·수정시각만 읽습니다. 파일 내용·해시는 읽지 않고 하위 폴더·링크는 건너뛰어 보고합니다.
- 최대 항목은 5000개입니다. 한도를 넘으면 완전한 보고서라고 주장하지 않고 오류를 반환합니다.
- 문서 등의 분류·가상 목적지와 항목 수·용량·이름 검토 표시를 반환합니다. `can_apply=false`이며 preview_id나 실제 이동 기능을 제공하지 않습니다.
- 파일 이름·수정시각도 개인 정보일 수 있으므로 외부 모델로 자동 전송·문서 인덱싱·영구 보고서 저장하지 않습니다. 이 도구의 응답은 요청한 사용자와 연결된 MCP 클라이언트에만 반환합니다.

## 검증과 다음 단계

새 모듈 스모크 검증과 영향 모듈 63개 테스트가 통과했습니다. 임시 프로젝트의 실제 MCP 미리보기→적용→undo 흐름, 충돌·변경·만료·타입·경로·중단·롤백 실패, 다운로드 내용 미열람을 확인했습니다. 실제 사용자 다운로드나 프로젝트 파일은 이번 개발에서 이동·조회하지 않았습니다.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_file_organizer.py tests/test_plugins.py tests/test_snapshots.py -q
python scripts/check_docs.py
```

내용 기반 분류·중복 내용 판단·외부 다운로드 쓰기·새 분류 규칙 사용자 설정은 후속 설계 과제입니다. 등록형 런처의 후속 구현은 [런처 안내](workflows.md)를 참조하세요.
