# 자비스 사용자 결정 — 자동 준비와 승인 정책

결정일: 2026-10-27 (Asia/Seoul). 근거: 이 채팅의 사용자 직접 지시와 선택 응답. 상태: 개발 요구사항 확정·일부 기술 기본값 위임, 런타임 구현/적용 완료 아님. 이 문서는 향후 구현의 정책 기준이며 실행용 승인 토큰이나 현재 가드레일을 우회하는 권한이 아니다. 실행 우선순위는 [PLAN](../PLAN.md), 개발·검증 절차는 [개발 규칙](../DEVELOPMENT.md)을 따른다.

## 사용자가 확정한 요구사항

1. 최초 사용은 사용자 승인으로 시작한다. PC 자원과 필요한 접근 권한의 위임 범위를 설명하고 기록한다. 자비스는 승인된 범위의 경로 탐색·요구사항 확인·다운로드·환경 구축·기동을 맡는다. 개발 중 이 문서를 작성하는 것이 실제 설치·예약 등록·서비스 기동을 지시한 것은 아니다.
2. 최초 구축 뒤에는 준비된 환경을 재사용한다. 매번 기동할 때 재설치·전체 다운로드하지 않는다. 누락·손상된 구성만 확인·복구하며 업데이트는 검증된 별도 정책에 따른다.
3. 사용자가 PowerShell에서 수신기나 각 서비스를 따로 관리하지 않아도 자비스 기동 시 승인된 기능이 준비되게 한다. 텔레그램·HUD·자동 배정·모델 연결은 각자 상태를 확인하고, 설정됨/설치됨/기동됨/연결됨/실제 기능 검증됨을 구분한다. 준비 자동화가 임의 작업 재실행이나 무조건적인 전체 기능 활성화를 뜻하지 않는다.
4. 외부 서비스 최초 로그인은 사용자가 ID/비밀번호를 직접 입력한다. 이후에는 저장된 인증 상태를 이용해 같은 승인 범위에서 자동 로그인한다. 비밀번호보다 세션/OAuth 토큰을 우선 재사용하고 암호화 보관한다. 사용자는 승인한 다른 기기로 인증 정보를 이전하는 것을 허용했다. 서비스가 세션 이전을 허용하지 않거나 만료·다중 인증이 필요하면 사용자에게 재인증을 요청한다.
5. 프로그램 삭제, 데이터 삭제, 파일·설정 등 변경은 대상·변경 목록·영향을 보여준 뒤 작업 단위로 한 번 승인받는다. 파일 100건인 한 작업을 파일마다 다시 승인받지 않는다. 포괄적인 PC 접근 위임만으로 임의 삭제·수정 목록을 승인된 것으로 간주하지 않는다.
6. 처음 승인한 범위를 넘는 예상 밖 변경이 필요하면 늘어난 범위만 추가 승인받는다. 기존 승인을 전체 작업 재승인으로 반복하지 않는다. 변경 대상·내용이 달라졌다면 기존 승인을 그대로 실행하지 않는다.
7. 사용자가 부재중이면 승인 필요한 부분만 대기하고, 해당 승인이나 결과에 의존하지 않는 허용된 작업은 계속한다. 연락이 없거나 시간이 지났다는 이유로 승인된 것으로 처리하지 않는다.
8. 외부 AI 전송은 서비스와 데이터 범위를 처음 승인받고 그 범위의 승인을 재사용한다. 다른 서비스·계정·데이터·목적 또는 범위 확대는 별도 확인한다. PC 자원 접근과 외부 전송 권한을 합치지 않는다.
9. 유료 AI/서비스 사용은 우선 건별 승인한다. 이후 예산 내 자동 사용 정책을 별도 결정한다. 현재 대화는 예산·유료 대체·무료 실패 후 유료 승격을 승인하지 않았다.
10. 중요 데이터만 기본 백업한다. 자비스가 이 정책으로 만든 복구용 사본은 30일 뒤 자동 정리한다. 이 승인 범위는 원본 데이터, 일반 문서·노트·대화, 작업 기록, 기존 다른 백업의 삭제를 포함하지 않는다. 실제 자동 정리는 소유권·보관 시작 시각·대상 범위를 검증하는 구현 이후 적용한다.
11. 사용자 로그인 시 자비스를 자동 시작하고, 창을 닫아도 백그라운드 작업은 계속한다. 창 닫기와 전체 종료/일시정지를 구분한다. 실제 로그인 자동 실행 등록은 아직 수행하지 않았다.
12. 다른 프로그램이 자원을 사용하면 그 프로그램을 우선하고 자비스 백그라운드 작업은 부하에 맞춰 최적화한다.

## 사용자가 자비스 판단에 맡긴 기술 기본값

- 기억: 선호·승인 정책·진행 중 작업·결과 요약을 기본으로 기억한다. 모든 대화를 무기한 보관하거나 자동 지식화하지 않는다. 인증 비밀은 일반 대화/기억/Obsidian 색인과 분리한다. 저장 정책 안내와 실제 실행 승인 원본은 별도이며, Markdown 기억을 실행 승인으로 쓰지 않는다.
- 다운로드: 실제 필요한 시점에 공식 출처·검증된 버전과 무결성을 확인해 준비한다. 기존 설치를 재사용하고 준비 기록을 남긴다. 저장 공간·기기 성능·전송 조건을 확인하며 큰 추가 부담이나 승인 범위 변경이 생기면 알려준다. 구체 용량/경로의 숫자는 이번 대화에서 고정하지 않았다.
- 자원: 사용자 프로그램을 우선하고 부하에 따라 작업 속도·동시 실행·추론 사용을 줄인다. 승인 대기와 자원 대기를 구분한다. 절전 해제나 절전 방지는 이번 응답에서 허용되지 않았다.
- 복구: 임시 위치의 준비→검증→적용, 중복 기동 방지, 소유 프로세스 확인, 제한된 재접속을 설계한다. 토큰 오류·중복 수신 충돌·부작용이 불명확한 발송/수정은 무조건 반복하지 않는다. 이는 기술 기본값이며 실제 설치나 업데이트를 수행한 기록이 아니다.

## 아직 확정하지 않은 세부

- 중요 데이터의 분류, 백업 실패 시 작업별 처리, 사본 용량 한도와 보관 유예/법적 보존 예외.
- 일반 대화 전문·감사 기록의 정확한 보관 기간. 30일은 이번에 정한 복구 사본에만 적용한다.
- 절전 해제·절전 방지, PC 전원 제어, 자원 제한의 구체 수치.
- 최초 자동 준비의 실제 설치 경로·용량·지원 구성, 업데이트 검증/복구 기준.
- 승인 철회·만료·다른 기기 신원 확인·인증 이전 방식과 기기 분실 대응의 세부 계약.
- 추후 예산 내 유료 사용 정책. 현재는 건별 승인 유지.

## 기존 개발 계획과 연결

- J0: 명시적 최초 위임, 작업별 변경 목록 승인, 범위 확대 재승인, 인증/기기 이전·철회, 외부 전송과 비용의 별도 경계. 기존 실행 직전 권한·해시·중단·예산 재검증을 유지한다.
- J1: 승인 부분 대기와 독립 작업 진행, 같은 요청 중복 실행 방지, 오류/불명확 상태에서 부작용 자동 재실행 방지.
- J2: 사용자 프로그램 우선 자원 배분, 기존 사용량/예산 정책 재사용, 유료 건별 승인.
- J3: 선별된 장기 기억, 비밀과 승인 원본의 분리. Obsidian은 승인 정책 안내·지식의 조회본이며 인증/실행 승인의 원본 저장소가 아니다.
- J4: 텔레그램/HUD/대화가 동일한 승인·실행 상태를 조회한다. Telegram T1은 현재 조회 전용이며 이 문서가 T2~T4를 구현한 것은 아니다. 원격 승인은 기존 작업/행동/대상/변경 해시/만료/nonce 계약과 연결한다.
- J5: 최초 환경 구축과 기동 관리·수명주기 통합. 기존 HUD/Dispatcher/Telegram poller/프로세스 관찰/워크플로를 재사용하고 두 번째 실행 엔진이나 기능별 별도 승인 체계를 만들지 않는다.

문서 반영 → 작은 준비 상태 점검 경로 → 최초 설정/권한 기록 → 승인된 구성의 통합 기동·종료/복구 순서로 기존 PLAN에 편입한다. 구현 담당과 순서는 PLAN/Board에서 조율하고 이 문서 자체를 자동 작업 배정 신호로 사용하지 않는다.
