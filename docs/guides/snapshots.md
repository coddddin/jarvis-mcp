# 프로젝트 스냅샷 — 백업·미리보기·복원

[문서 안내](../README.md) · [현재 계획](../PLAN.md)

## 이번 구현 범위

`JarvisWorkspace/projects/<프로젝트명>/` 디렉터리의 일반 파일을 ZIP과 SHA-256 목록으로 백업합니다. 초기 구현은 이 데이터 영역만 허용하며 자비스 서버 운영 코드, 외부 다운로드 폴더, PC 전체 백업은 지원하지 않습니다. 기존 파일 권한을 확대하거나 서버 코드를 작업공간으로 옮기지 않았습니다.

복원은 **병합 방식**입니다. 스냅샷에 포함된 파일만 복구하고, 백업 후 추가된 파일·기본 제외 파일은 유지합니다. 전체 디렉터리를 특정 시점과 완전히 같게 만드는 삭제 동작, 빈 디렉터리·권한·소유자·파일 생성 시각 복원은 제공하지 않습니다.

## 사용 순서

1. 백업할 프로젝트를 `JarvisWorkspace/projects/demo/`처럼 준비합니다. 자동으로 외부 프로젝트를 복사하거나 인덱싱하지 않습니다.
2. 자비스 서버를 재연결해 새 도구 4개를 불러옵니다. Codex에서 보이지 않으면 앱을 재시작합니다.
3. `create_project_snapshot(project="projects/demo")`로 백업하고 반환된 `id`, 파일 수, 제외 목록을 확인합니다.
4. 필요할 때 `list_project_snapshots()`로 백업과 미완료 복구 작업을 조회합니다.
5. `preview_project_restore(snapshot_id="반환된 32자리 id")`로 생성·교체될 파일을 확인합니다.
6. 사용자가 해당 변경의 복원을 요청·승인한 범위에서 `restore_project_snapshot(preview_id="미리보기 id")`를 호출합니다. 승인되지 않은 실제 사용자 파일을 검증 목적으로 덮어쓰지 않습니다.

미리보기는 10분 동안 유효하고 한 번만 사용할 수 있으며 서버 재시작 시 무효화됩니다. 미리보기 뒤 대상 파일 또는 백업이 바뀌면 거부하므로 새 미리보기를 확인해야 합니다. 미리보기 ID는 검토한 상태를 결합하는 수단이며 사용자 신원을 인증하는 별도 승인 시스템은 아닙니다.

## 백업 정책

- ZIP과 메타데이터는 `JarvisWorkspace/.jarvis-snapshots/`에 보관합니다. 원본 프로젝트와 달리 숨김 보관 영역이므로 문서 인덱싱에서 제외됩니다.
- 숨김 파일·폴더, `venv`, `node_modules`, `__pycache__`, `dist`, `build`, `sources`, `client_secret*`, `.pem/.key/.p12/.pfx`는 기본 제외하며 목록을 보고합니다. 파일 이름 기반 규칙이므로 일반 코드에 하드코딩된 비밀정보까지 탐지하지는 못합니다.
- 링크·정션·하드링크·특수 파일은 거부합니다. 파일 500개, 파일당 5MB, 합계 25MB, ZIP 30MB, 탐색 항목 2000개, 하위 디렉터리 깊이 20이 상한입니다. 용량은 1MB=1,000,000바이트 기준입니다.
- 최대 ZIP/메타데이터 수와 복구 기록 수는 각각 100개입니다. 자동 삭제하지 않고 상한에서 거부합니다. 불완전 생성으로 남은 ZIP도 용량 계산에 포함하므로 운영자가 보관·정리해야 할 수 있습니다.
- 파일 내용은 보존하지만 제외 항목·빈 디렉터리·메타데이터까지 포함하는 완전한 OS 이미지 백업은 아닙니다. 파일별 순차 읽기이므로 쓰기 작업을 멈춘 상태에서 백업하는 것이 적절합니다.
- ZIP과 메타데이터는 암호화·서명되지 않습니다. 체크섬은 손상을 탐지하며 공격자가 ZIP과 메타데이터를 모두 변경할 수 있는 환경에서 진본을 보증하지 않습니다. 외부 ZIP을 가져와 복원하는 기능은 제공하지 않습니다.

## 복원과 실패 처리

- 복원 직전 현재 프로젝트를 자동 백업합니다. 프로젝트가 사라진 경우 복원 전 파일이 없으므로 해당 백업 ID는 null입니다. 변경할 파일이 없는 경우에는 백업·파일 교체 없이 반환합니다.
- 모든 ZIP 경로·중복·특수 항목·파일 크기·합계·해시를 검사합니다. `extractall`로 파일을 풀지 않으며 작업공간 밖 경로와 숨김·보호 항목을 허용하지 않습니다.
- 임시 파일과 원래 파일 사본을 준비한 뒤 파일별로 원자적 교체합니다. 복원 전에 대상을 다시 검증하고 오류가 나면 이미 적용한 파일을 되돌립니다. 새로 생성한 파일은 롤백 시 제거하고 기존 추가 파일은 유지합니다. 실패 뒤 빈 디렉터리가 남을 수 있습니다.
- 복원 기록은 `.jarvis-snapshots/recovery/<recovery_id>/journal.json`에 남습니다. `planned` 순서의 i번째 파일에 `new-i`와 해당하는 기존 파일 사본 `old-i`가 대응하며 백업 ID도 기록합니다. 성공한 작업의 기록·사본도 자동 삭제하지 않습니다.
- 롤백 실패·프로세스 강제 종료 등으로 미완료 기록이 남으면 `list_project_snapshots`의 `pending_recoveries`에 표시하고 추가 복원을 막습니다. 운영자가 현재 파일·journal·old 사본·사전 ZIP을 대조해 복구해야 하며 이번 버전은 장애 후 자동 복구 도구를 제공하지 않습니다. 확인 없이 journal을 지워 잠금을 우회하지 마세요.
- 복원 중 대상이 외부 프로세스에 의해 다시 변경되면 그 파일을 롤백으로 무조건 덮어쓰지 않고 복구 실패로 보고합니다. 여러 파일 전체에 대한 단일 트랜잭션이나 전원 차단 시 완전한 원자성을 보장하지 않습니다.
- 기존 경로 가드레일은 OS 샌드박스가 아니며 동시 경로 변경 경쟁 조건의 한계는 유지됩니다. 임시·기존 파일 사본에도 원문이 포함되므로 보관 디렉터리를 운영자 전용으로 관리해야 합니다.

## 예산·중단·자동화 상태

4개 도구도 공통 프로세스 20회 호출 예산을 사용합니다. 내부 파일 작업마다 예산을 다시 차감하지 않습니다. 스냅샷 순회·스테이징·파일 교체 사이에서 `.jarvis-stop`을 추가 확인하고, 적용 중 중단되면 롤백을 시도합니다. 이미 진행 중인 개별 파일시스템 호출을 강제로 종료하거나 모든 기존 도구를 즉시 중단시키는 기능은 아닙니다.

복원 직전 백업만 자동입니다. 주기 예약, 모든 코드 수정 전 자동 후크, 다른 도구와의 자동 연결은 아직 구현하지 않았습니다. 다음 파일 정리·수정 도구에서 이 서비스를 재사용할 수 있습니다.

## 검증

실제 사용자 프로젝트는 복원하지 않고 임시 프로젝트로 테스트했습니다. 기존 8개 계약과 신규 4개 등록, ZIP 검증·체크섬·만료·대상 변경 거부·사전 백업·파일 보존·스테이징 실패·부분 적용 롤백·롤백 실패·중단·실제 stdio MCP 복원 흐름을 확인합니다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
python scripts/check_docs.py
```
