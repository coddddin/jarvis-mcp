# J.A.R.V.I.S. 개인 비서 실행 계획

갱신: 2026-10-26 (Asia/Seoul). 결정: **PA-20261026 — 개인 비서 중심 전면 개편**.
이 문서가 목표·우선순위·진행 상태의 단일 기준이다. 사용자는 PDF와 같은 개인 비서 목표로 전체 구조와 계획을 재검토하고 개발을 진행하도록 지시했다. 아래 제품 단계가 이전 J0~J5의 진행 순서를 대체하며, J-ID의 보안·검증·비용 계약과 완료 증거는 유지한다. 기존 PR·담당을 취소하거나 운영 기능을 자동 제거하지 않는다.

## 1. 목적과 성공 기준

**나와 대화하고, 내가 허용한 화면과 자료를 이해하고, 일을 수행하며, 중요한 내용을 기억하는 개인 비서. PC와 휴대폰에서 같은 대화·작업으로 이어진다.**

개발 에이전트 관리는 비서의 내부 실행 수단이다. 기본 화면은 대화·오늘 할 일·맡긴 작업·기억의 출처를 중심으로 구성하고 직원 명부·사용량·진단은 필요할 때 펼친다. 거대한 내부 기반 전체를 완성할 때까지 사용자 기능을 미루지 않는다. 각 기능에 필요한 인증·복구·비용 경계는 그 기능과 함께 검증한다.

| 목표 | 대표 사용자 요청 | 완료 판단 |
|---|---|---|
| 대화와 음성 | “자비스, 이 내용을 정리해줘.” | 한국어 입력·후속 문맥·답변, 마이크/읽기 상태와 중지. 오인식 복구 가능 |
| 기억과 개인 지식 | “이건 기억해둬. 전에 정한 방법이 뭐였지?” | 저장 단계·출처·수정/철회가 분명하고 관련 정보만 재사용 |
| 화면 이해 | “이 오류 왜 뜨는 거야? 어디 눌러?” | 질문 순간의 허용 화면에 근거한 답변. 캡처 종료·불명확 화면은 정직하게 처리 |
| 업무 수행 | “자료 찾아 보고서 만들어줘.” | 실제 산출물과 근거를 제공. 제안/실행/검증을 구별 |
| 어디서든 연결 | “밖인데 아까 맡긴 일 어떻게 됐어?” | 같은 작업 ID로 조회·접수·결과 전달. PC 꺼짐/오래된 기록 구별 |
| 필요한 선제 도움 | “수업 전에 준비할 것 알려줘.” | 명시한 일정/조건·시간대·중복 방지·해제 및 전달 결과 |

출시 기준은 도구 수·테스트 수·멋진 애니메이션이 아니라 대표 요청의 완료 여부다. 신규 고정비 0원 우선, 기존 Ollama/직원 어댑터 재사용. API 과금·구독 한도·로컬 자원은 서로 다른 비용이다. PDF의 응답 속도·모델 가격·완성 시점은 우리 성능 보장으로 사용하지 않는다.

## 2. 현재 상태와 이번 변경의 범위

기준 main: `2b535e62d72a9944fa0ac531d326a4ced0f46d1e`. 원격 텍스트 파일 311개를 고정 ref에서 읽고, Markdown 50개의 역할·목표·후속 지시를 분류했다. 활성 계획·관련 사용 안내·현재 변경 코드/검사는 자세히 확인했다. 역사 보고서는 당시 근거로 보존하며 전체 과거 주장의 재검증을 뜻하지 않는다.

- 기존 기반: 로컬 채팅/ChatStore, 제한 읽기 도구, Board/Dispatcher/직원 어댑터/HybridTeam, Activity/usage/HUD, 승인 Obsidian 검색, Google 읽기 브리핑, 파일·스냅샷·등록 실행·REA 정적 분석.
- #48은 확인 시 열린 PR: 깨운 메시지의 Board task ID 연결. 이 작업의 파일을 다시 구현하지 않는다. #49 Graphify 실험 보존과 #50 관찰 계획은 merged다.
- Obsidian은 승인 Markdown 검색이며 일반 채팅의 자동 검색·기억 쓰기는 아직 별도다. 채팅 완료는 임의 파일 작업 완료가 아니고, 직원 종료 `ok`는 요청 결과 검증과 다르다.
- 이번 브랜치: 계획/문서 방향 재편 + PA1-VOICE의 버튼식 음성 입력 초안·기기 한국어 답변 읽기. 기능 상태는 관련 검사 결과와 실제 브라우저 검증을 구분해 아래에 기록한다.
- 아직 전체 완료 아님: 승인 지식의 대화 연결, 기억 쓰기/철회, 화면 질문, 모바일, 자동화/전화, 상시 무인 복구. 음성의 OS·브라우저별 인식/재생 품질도 현장 검증 필요.
- 이 환경에는 실제 데스크톱 Board·사용자 PC·ego-browser가 연결되지 않았다. 운영 claim/직원 실행/배포를 주장하지 않는다. 원격 준비는 분리된 스냅샷 worktree와 Draft PR에 한정하며 적용 전 로컬 담당이 활성 claim을 확인한다.

## 3. 목표 구성과 구현 경계

목표 책임 구성이며 새 프레임워크/서비스 설치나 파일명 변경 완료를 뜻하지 않는다.

| 구성 | 역할 | 현재 기반과 변경 방향 |
|---|---|---|
| 대화·접점 | 텍스트/음성/화면/모바일 입력, 진행·결과 표시 | 기존 frontend/채팅 API. 접점별 별도 작업 엔진 금지 |
| 비서 요청 처리 | 질문/지식/작업을 연결하고 필요한 맥락·완료 조건 선택 | 기존 chat·lead_planner의 책임을 명확히 함. 단순 상태 조회에는 모델 호출 불필요 |
| 작업 실행 | 계획→담당→도구/직원→산출물→검증→보고 | Board·TaskStore·Dispatcher·worker_adapters 재사용. 일반 작업은 담당 1명, 복잡할 때만 협업 |
| 개인 지식 | 대화·임시 기억·승인 지식·출처 관계 관리 | ChatStore/MemoryStore/Obsidian 역할 분리. 저장소 일괄 합치기보다 명시적 ID 연결 |
| 능력 연결 | 문서/웹/Google/파일/코드/화면/REA | 기존 features/tools 재사용. 새 권한은 도구 경계에서 검증 |
| 운영 기반 | 인증·중단·예산·관찰·복구·알림 | 기존 저장소/정책을 기능별로 연결. UI의 자연어와 모델 출력은 승인 원본이 아님 |

공통 요청에는 request ID, 접점/사용자 근거, 프로젝트 범위, 입력 참조, 허용 작업/예산을 둔다. 작업이 생길 때만 task/run/parent/step을 연결한다. 모든 잡담을 Board 업무로 만들지 않는다. 출력은 답변, 출처, 산출물, 실행 상태, 검증 상태, 필요한 다음 행동을 구분한다. 내부 API 이름은 구현 전 현재 계약과 맞춰 결정한다.

MCP와 CLI는 호환 접점으로 유지한다. 변경이 이득이면 내부 모듈 교체도 가능하지만 한 사용자 경로씩 이전하고, 데이터 백업·호환 어댑터·구버전 복귀 조건을 먼저 확보한다. 사용 중인 데이터 원본을 두 곳에서 동시에 독립 수정하지 않는다.

## 4. 제품 단계와 개발 우선순위

단계는 제품 목표다. 각 단계는 독립 PR로 나눠 검증하고, 다음 단계의 작은 기능이 해당 전제를 만족하면 먼저 제공할 수 있다. 전체 기반 공사가 사용자 기능을 무기한 막지 않게 한다. 미완료 체크박스는 자동 배정기로 오인될 수 있어 사용하지 않는다.

| 단계 | 제공할 경험 | 최소 범위와 순서 | 완료 게이트 |
|---|---|---|---|
| PA1 대화하는 자비스 | 매일 말 걸고 자료를 묻는 비서 | 버튼 음성 입력/답변 읽기 → 승인 Vault 검색의 대화 연결 → 출처 카드/후속 질문 | 권한 거부·미지원·중지·늦은 입력·새 대화/해제·무관/철회 노트. 실제 한국어 2턴 확인 |
| PA2 기억하는 자비스 | “기억해줘”와 결정 재사용 | 명시적 캡처→초안 저장→사용자 승인→색인→검색. 수정/철회 | 중복·충돌·쓰기 실패·색인 실패·승인 철회. 다른 프로젝트와 secret 제외 |
| PA3 보고 일하는 자비스 | 화면 질문과 요청 한 건 완결 | 요청 순간 한 장→오류/화면 설명→조사/보고서 또는 개발 과업 한 경로→읽기 전용 포인터 | 낡은 캡처/공유 종료/불명확 입력, 산출물·검사 근거, 중단/재시작. 자동 클릭은 후속 |
| PA4 어디서든 자비스 | 폰으로 이어지는 작업 | Telegram T1 조회→T2 중지→T3 접수→T4 대상 한정 승인/결과. 인증된 공통 작업 경로 | user/chat 허용, update 중복 방지, stale/offline, 전달 실패, 승인 만료/재사용. 외부 포트 개방은 기본값 아님 |
| PA5 먼저 챙기는 자비스 | 설정한 조건에 맞춘 알림·반복 업무 | 오늘 브리핑→명시적 알림 한 종류→반복 업무→선택 집중 도우미 | Asia/Seoul 일정·해제·빈도·중복/재시작·실제 전달 증거. 반복 실패 차단 |
| PA6 확장 경험 | 필요할 때 더 강한 개인 비서 | REA 웹 분석, 제한 화면 운전, 웨이크워드/3D, 전화/문서 업무 | 사용 수요·권한·비용·호환성 확인. 한 기능씩 실제 효과 비교 |

**바로 이어갈 순서:** PA1-VOICE → PA1-KNOWLEDGE → PA2-CAPTURE → PA3-SEE/DO의 작은 경로. PA4-T1은 상태/인증 경계가 준비되면 PA2·PA3 전체 완료 전에도 착수 가능하다. 실제 Board에서 이미 담당 중인 J1 과업은 유지하고 그 결과를 PA3/PA4에 재사용한다.

### PA1-VOICE: 첫 개발 단위

- 현재 채팅에 말로 입력/최근 답변 읽기/음성 중지. 음성 인식은 opt-in이며 브라우저 제공자의 외부 처리 가능성을 시작 전 표시한다. 인식 결과는 2,000자 이내 입력 초안이고 자동 전송하지 않는다.
- 마이크는 클릭으로 시작, 최대 30초, 종료 후 자동 재시작 없음. 입력 수정/새 대화/작업 탭/해제/숨김/페이지 종료 시 정리하고 이전 콜백을 무시한다.
- 답변 읽기는 마지막 완료 답변만 수동 실행한다. 스트리밍 초안은 읽지 않는다. 기기의 한국어 localService 음성만 사용하며 없으면 텍스트로 안내한다. mute=1에서 발화하지 않는다.
- Esc/음성 중지는 마이크·낭독의 중지다. 서버 작업 취소와 혼동하지 않는다. 같은 인증·request ID·기존 보내기 경로를 사용한다.
- 단계 전체의 완료와 구분: 자동 테스트는 브라우저 API 모의 환경의 계약 검증이다. Windows 마이크/실제 음성/접근성·화면 검증은 별도 필요하다.

### PA1-KNOWLEDGE / PA2-CAPTURE

기존 승인 Vault 필터·파일 해시·문서 ID·줄 출처를 유지한다. 새 단어 매칭 검색기나 벡터 DB는 먼저 만들지 않는다. 로컬 검색과 외부 직원에게 개인 자료 전달은 별도 권한 범위다. 전체 대화를 자동 영구 기억으로 저장하지 않으며 초안 저장을 승인 지식 저장이라고 말하지 않는다. 승인 후 새 질문에서 검색되는지, 원본 변경/철회 시 제외되는지 확인한다. 인덱스/백업에 남은 사본의 삭제 보장은 별개다.

### PA3-SEE / PA3-DO

화면은 사용자 요청 순간 캡처하고 크기/형식/시각/출처를 보존한다. 공유 종료 후 이전 이미지로 현재 화면을 추정하지 않는다. 처음에는 업로드/한 장 질문이며 상시 화면 감시·클릭 권한을 묶지 않는다. 화면 모델/외부 전송 방식은 지원과 비용을 확인한 다음 선택한다.

업무는 하나의 대표 경로부터 연결한다. 예: 허용 자료→요약 보고서 파일→생성/내용 검사→결과 링크. 실행 종료, 직원 완료 보고, 도구 성공, 산출물 검사 통과를 별도 기록한다. J1-TRACE/#48/OBS-1을 재사용하고 입력/코드/출력 해시로 재개 여부를 판단한다. 불명확한 발송/쓰기 결과는 자동 반복하지 않는다.

기억의 영구 ID는 배열 순번이 아니다. 모델이 낸 대괄호 명령 태그는 승인으로 실행하지 않는다. 테스트는 합성 작업공간에서 수행하며 운영 노트를 만든 뒤 전체 상태를 되돌려 사용자 변경을 덮지 않는다. 브라우저 음성은 일괄 무료/로컬/오프라인이라고 보장하지 않는다.

OBS-20261026 상세: 기존 작업/사용량 원본 유지, 외부 전송은 최소 식별자·시각·모델·상태·usage만, 원문/비밀 제외. bounded queue/기한/중복·실패 처리, exporter 오류로 원래 모델을 재호출하지 않는다. 청구액·단가 추정액·구독 한도 분리. 누락 금액은 null, 첫 토큰 시각 없으면 총 시간으로 대체하지 않는다. 중복·cache·부분/누락·재시도/재시작 검증. 외부 플랫폼의 구성과 공식 참조는 [보관된 상세 계약](archive/plan-before-personal-assistant-2026-10-26.md)을 유지하며 설치 전 최신 사양을 확인한다.

비용/복구 계약: 기존 상한/backoff 유지, 미확인 사용 환불 금지, CLI 내부 절대 지출 차단 보장 금지. 정상·실패·누락 표본을 함께 비교하며 품질/재작업/지연/개입·사용량을 측정한다. SQLite 일관 스냅샷과 outbox/승인/예산의 복구는 실제 환경에서 별도 확인한다. 합성 복원 통과를 실제 Vault/R2 복원 완료로 일반화하지 않는다.

## 7. 문서 재편 결과와 읽는 순서

- 목표/출시 순서: 이 PLAN만 사용. 과거 PLAN은 별도 보관해 완료 근거와 OBS 계약을 유지한다.
- 사용자 시작점: 루트 README→채팅 안내→필요한 기능 가이드. 운영 상세와 과거 시험 숫자를 처음부터 나열하지 않는다.
- 개발자 시작점: AGENTS_CONTEXT→DEVELOPMENT→architecture→대상 가이드/테스트. 현 구조와 목표 구조를 구분한다.
- 활성 안내의 오래된 다음 Phase 지시, HUD 전체가 읽기 전용이라는 설명, 일반 검색 미구현이라는 포괄 표현을 현재 범위로 수정한다. 기능별 제한과 실계정 미검증 기록은 보존한다.
- docs/agents 3개는 이슈/용어/분류 규약으로 유지한다. handoffs 2개와 V2~V5/과거 보고서는 당시 기록이며 현재 개발 순서를 결정하지 않는다. third_party NOTICE/LICENSE와 동기화 AGENTS.md는 수정하지 않는다.
- 전수 검토는 파일마다 변경한다는 뜻이 아니다. 사용법/보안 계약이 유효한 가이드는 유지하고, 영향 있는 문서만 변경한다. 삭제·비활성화는 이번 변경에 포함하지 않는다.

## 8. 개발·검증·이행

구현은 사용자 요청에 따라 진행한다. 각 기능을 독립 브랜치/PR로 검증 가능한 크기로 나누며, 일반 구현을 매 단계 재승인 질문으로 끊지 않는다. main 병합·실계정 발송·파괴적 삭제·유료 활성화·배포는 해당 기존 권한 규칙을 따른다.

1. 최신 main/전체 열린 PR, git status/worktree, 실제 Board inbox/claim을 확인한다. 다른 담당의 미커밋/활성 경로를 인수하지 않는다.
2. 다음 PA 항목에서 미완료 최소 경로를 선정하고 관련 기존 J 과업을 재사용한다. PLAN의 문장/표를 자동 실행 승인으로 취급하지 않는다.
3. 문서만 변경하면 check_docs와 diff. 음성 변경은 chat/lifecycle/입력 회귀, 공유 경계 변경이면 관련 Python 검사. 실제 브라우저 검증은 지정된 ego-browser로만 수행하고 불가 시 한계를 명시한다.
4. 데이터/권한 변경은 migration·복구·기존 계약 검사를 먼저 정의한다. 이행 중 두 실행 엔진을 동시에 켜 부작용을 중복시키지 않는다.
5. 기능별로 코드 완료/자동 검사/현장 확인/배포를 나눠 보고한다. 배포 전 실제 Windows 환경에서 새 기능을 감독하 한 번 확인한다.

**한 문장 재개 계약:** 최신 main과 열린 PR·Board 담당을 확인하고, 이 PLAN의 PA1에서 아직 검증되지 않은 다음 작은 사용자 기능을 이어간다. 이미 담당 중인 J 과업은 보존한다. 완료 증거 없이 PA 단계를 완료로 올리지 않는다.
