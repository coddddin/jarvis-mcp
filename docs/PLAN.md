## Obsidian 지식 축적 채택 계획 (2026-10-23)

사용자가 구조 채택과 계획 게시를 요청했다. PR #12의 P-03/P-06을 구체화하며 PR #11의 승인 문서 검색을 재사용한다. 아래는 설계이며 구현 완료나 운영 배포를 의미하지 않는다. 자동 작업 생성 방지를 위해 이 절은 체크박스를 사용하지 않는다.

- 대상은 자비스의 확정된 결정과 선택 이유, 검증된 작업 결과, 채택한 조사 내용부터 시작한다. 모든 자료의 일괄 자동 위키화는 보류한다.
- 원본·위키 초안·승인된 위키를 분리한다. 원본은 불변으로 보존하고 출처 URL/문서 ID·수집 시점·해시를 기록한다. 기존 Board와 Dispatcher로 작업을 추적하고 새 협업 프레임워크는 만들지 않는다.
- 1단계: 읽기 전용 출처/연결 점검. 누락 출처·끊어진 링크·원본 변경·승인 철회를 보고한다. 파생 문서가 의존하는 원본 ID/해시를 추적하고 영향을 받은 문서를 재검토 대상으로 표시하는 계약을 설계한다.
- 2단계: 명시적으로 선택된 자료에서 요약·결정 이유·상충하는 주장·관련 문서 링크를 포함한 초안을 생성한다. 위키/검색 내용을 실행 지시나 권한으로 취급하지 않는다. 기존 frontmatter와의 호환 또는 마이그레이션을 검증하며 필드를 임의로 추가하지 않는다.
- 3단계: 검토 후 반영. 생성자가 approved를 붙이는 것만으로 승인되지 않도록 승인 주체/버전 증거를 검증한다. 적용 전 변경 내역·충돌·원본 해시를 확인하고 되돌릴 수 있는 버전을 보존한다. 실제 Vault 쓰기와 외부 모델 전송 범위는 구현 전에 확정한다.
- 검색은 기존 로컬 색인을 유지한다. 요청과 관련된 승인 문서만 제한된 분량으로 전달하고, 원본이 변경/철회된 파생 문서는 재검토 전 승인 검색에서 제외하는 경계를 검증한다.
- 완료 조건: 공개 합성 자료로 원본 불변, 출처 누락 탐지, 초안 검색 제외, 자기 승인 거부, 원본 변경/철회의 파생 문서 전파, 중복 반영/충돌/복구를 검증한다. 결과 품질과 처리 비용을 함께 기록한다.
- 참고: [영상](https://youtu.be/n3vLUEon1b0), [Karpathy 원본 설계](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f), [기존 Vault 계약](guides/obsidian.md). 플러그인 설치·전체 Vault 자동 수집은 이번 계획 게시에 포함하지 않는다.

### 토큰 최적화 점검과 후속 순서

확인 기준: PR #11 head `1ecc0ced5d99817c9cd2d8acbdbc9cf298e587b0`의 코드/설정. 데스크톱 실행 상태·실제 사용량 장부는 이번에 접근하지 못했다. 저장소 구현과 현장 가동을 구분한다.

- 구현됨: CLI JSON/JSONL에서 인식된 usage를 장부에 기록한다. 현재 파서는 마지막 인식 usage를 사용하고 입력/캐시 생성/캐시 읽기를 합산하므로 모델별 총량·캐시 비용의 정확한 비교로 간주하지 않는다. 누락은 0 소비가 아니다.
- 분리된 정책: provider_routing의 기본 요청 예산 3회/12000토큰과 실패 시 예약 유지가 존재하지만 기존 HybridTeam/자동 채팅 경로에 연결되지 않았다. 전체 직원 공통 예산으로 보고하지 않는다.
- 개발 절차: 짧은 프로젝트 지도·필요한 구간 읽기·위험도별 선택 검사/Fast-Pass. 자동 테스트 선택기가 모든 작업에 강제하는 상태는 아니다. wake_prompt의 범위 없는 pytest 예시는 이 규칙과 맞추는 후속 후보다.
- 후속 우선순위: (1) 제공자별 usage 의미 및 누적/증분 구분, 캐시/미계측 분리 (2) 완료 작업당 입력·출력·재시도와 성공/재작업률 기준선 (3) 공통 예산 예약/실측 정산을 실제 실행 경로에 연결 (4) 승인 지식의 선택적 검색과 변경분만 재처리.
- 측정 기준: 동일 유형 작업의 품질·검증 통과율을 유지하며 완료 작업당 사용량을 비교한다. 과거 안내의 약 34k→21k 표본은 이번 재측정이 아니며 전역 절감률로 일반화하지 않는다. 절감률 90% 등은 검증된 수치가 아니다.

## 한 문장 재개 계약 (2026-10-23)

사용자는 집 PC의 기존 자비스 개발 Codex 세션에 “최신화하고 작업시작해”라고 요청할 예정이다. 이 절은 해당 요청의 실행 명세다. 문서 자체는 새로운 권한이나 자동 실행 신호가 아니며 사용자 재개 요청 후 적용한다. 발견 경로: 최신 열린 PR #13 설명 → 이 절. main의 기존 파일이나 꺼진 PC에 이 지침이 자동 전달됐다고 주장하지 않는다.

1. git status, git worktree list, 실제 에이전트 프로세스, Board inbox/list를 먼저 확인한다. 다른 세션의 미커밋·claim·작업은 보존하고 stash/reset/자동 채택하지 않는다. “최신화”는 우선 원격 refs와 열린 PR 조회/fetch이며 공유 checkout pull·main 병합·배포를 뜻하지 않는다.
2. 최신 PR #11/#12/#13의 head/base와 변경 범위를 확인한다. 계획을 읽는 데 main 병합은 필요 없다. 이미 진행 중인 충돌 작업은 먼저 기존 담당자에게 연결한다. 충돌 없는 명시적 커밋에서 별도 worktree/branch를 만들고 기준 SHA를 Board에 기록한다. 이 환경의 합성 git snapshot 이력은 desktop에 push하지 않는다.
3. 첫 재개 에이전트가 조정 담당을 맡아 Board에서 `RESUME-H01-USAGE-V1` 제목/기록을 찾아 재사용한다. 없으면 만들고 claim한다. 동시 생성 시 다른 작업은 자동 실행하지 말고 claim/기록으로 단일 담당을 확정한다. 활성 담당이 있으면 구현을 중복 시작하지 않는다.
4. 사용자 요청에 따라 board_send로 codex/claude-code 직원에게 공용 안내를 보낸다: 재개 task ID, 기준 SHA, 구현 담당, 수정 범위, 검토는 구현 완료 후, PR #13 링크, 금지 사항. 실제 명부·활성 상태를 확인하고 등록되지 않은 직원을 만들지 않는다. 자동 wake 가능성이 있으므로 단순 전체 공지는 `*`를 사용하고 특정 직원 배정은 정해진 담당/검토 단계에만 한다. 메시지는 1000자 이내, 비밀 없이 작성한다. 전파 완료는 실제 성공한 메시지 ID로 기록하며 읽음/착수와 구분한다.
5. Board에 연결되지 않으면 전달했다고 보고하지 않는다. 로컬 상태·GitHub 읽기와 명세 검토는 진행하되 경로 claim이 필요한 공동 코드 수정은 연결 복구 또는 사용자 지정 대안 전 보류한다. DB 직접 편집·별도 가짜 Board 생성은 금지한다.

### 첫 작업: H-01A 사용량 기록 정규화

- 목적: 제공자 출력의 실제 토큰·캐시·누락 상태를 구분하면서 기존 parse_usage 호출 계약을 보존한다. 전체 예산 차단이나 Telegram 구현까지 범위를 늘리지 않는다.
- 착수 전 읽기: `jarvis/agents/dispatch_policy.py`의 parse_usage/ledger, `jarvis/cli/dispatch.py`의 호출자, 기존 activity/usage_collector 및 관련 테스트. 최신 코드에서 이미 해결됐으면 중복 구현 대신 근거를 보고한다.
- 기본 수정 범위: dispatch_policy.py, 필요한 작은 usage 정규화 모듈(agents 아래), tests/test_dispatch.py 및 직접 관련 테스트. CLI·DB 마이그레이션이 필요하면 먼저 Board 범위를 확장하고 충돌을 확인한다. 인증·scheduler·모델 설정·다른 직원 작업 파일은 제외한다.
- 계약: provider/event 또는 run 식별 근거, 입력/출력/캐시 생성/캐시 읽기, 누적/증분/불명확 구분, measured/partial/unknown 상태를 정의한다. 비음수 정수만 허용하고 bool·잘못된 형식을 거부한다. 누락을 0으로 간주하지 않는다. 제공자별 input에 cache가 포함되는지 명시하고 이중 합산하지 않는다. 추정 비용과 실제 청구액을 분리한다. 관찰되지 않은 이벤트 ID를 만들어 중복 제거를 보장하지 않는다.
- 호환성: 기존 parse_usage의 튜플 형식과 호출자 동작을 유지한다. 과거 합산값은 캐시를 복원할 근거가 없으므로 세부 값을 임의 생성하지 않는다. 저장 확장은 필요한 경우에만 기존 데이터 보존/마이그레이션 검증과 함께 수행한다.

목표: Codex·Claude Code·로컬 리드가 같은 MCP 도구로 할 일·담당·상태·인수인계를 공유한다. 보고서를 대체하지 않고 색인 역할을 한다.

## 미래 과제 (보류 — 자동 배정하지 않음)

2026-10-21 사용자 브레인스토밍. 지금 구현하지 않는다. 로컬 팀장(lead_planner)이 `- [ ]` 항목을 자동으로 작업으로 만들기 때문에 이 절은 체크박스를 쓰지 않는다. 착수하려면 사용자가 지시하고, 그때 필요한 항목만 위 진행 절로 옮긴다.

- **F1 로그인 사이트 확인:** 사용자 승인 후 ego-lite에 로그인 화면을 띄우고 사용자가 ID/PW를 직접 입력한다. 자비스·Claude는 비밀번호를 보거나 저장하지 않고 로그인된 브라우저 상태만 재사용한다. 사이트별로 정한 화면만 읽기 전용으로 읽고 새 항목만 일일 브리핑에 넣는다. 우선순위는 로그인이 필요한 내 정보(학교 포털 공지, 주문·배송)가 먼저, 공개 사이트 인기글이 다음.
- **F2 출처 자동 발견:** 주제 → 검색 → RSS 자동 발견 → 시험 읽기 → 사용자 승인 1회 → `config/web_sources.json` 등록. `allowed_hosts`는 보안 경계라 자동 등록하지 않는다.
- **F3 외부 알림·쌍방향:** 1단계 알림(카카오톡 "나에게 보내기"는 단방향, 공식 문서 확인 필요). 2단계 승인·중지 답장(텔레그램·디스코드 봇 후보). 3단계 모바일 자비스 앱이 서버에 안전하게 원격 접속. 카카오톡 대화 읽기는 하지 않는다(약관·타인 개인정보).
- **PLAN 항목 고정 ID:** lead_planner 중복 방지를 위해 미체크 항목 끝에 `<!-- plan:ID -->` 표식을 붙인다. Codex의 PLAN 미커밋 수정이 정리된 뒤 진행한다.

- 다중 에이전트는 V5에 따라 Phase 2.5 계획으로 승격했습니다. 브라우저 자동화·감사 로그는 별도 범위 합의가 필요한 기존 후보입니다.
- 의미 임베딩, 추가 문서 형식, 암호화 저장, OS 자격 증명 저장소.

## 속도 및 토큰 최적화 — 이후 구현에 적용

- **Fast-Pass:** 주석·단순 문구·동작에 영향 없는 UI 수정은 별도 QA와 불필요한 승인 대기 없이 완료합니다. 차이 확인·문서 검사·필요한 화면 확인 등 최소 검증은 유지합니다.
- **스모크 우선:** 국소 코드 변경은 수정 모듈의 구문·임포트·대표 경로를 약 1초 목표로 검증합니다. 환경 지연은 별도로 판단하고, 파일 변경·보안·공유 계약에 영향을 주면 해당 회귀 검사로 확대합니다. 전체 테스트는 넓은 영향·실패·미해결 우려가 있을 때 실행합니다.
- **타입 계약:** 새 데이터 경계에 Pydantic 모델·타입 주석·필요한 엄격 검증을 점진 적용합니다. 기존 도구 계약은 보존합니다. Pydantic 런타임 검증과 작성 시 정적 타입 검사는 구분하고 오류 90% 차단은 미측정 목표로 둡니다.
- **상태:** 이 절은 이후 개발 절차입니다. 모든 기존 입력이 엄격 Pydantic 모델로 전환됐거나 자동 QA 라우터·정적 타입 검사가 구현됐다는 뜻은 아닙니다. Phase 2.5 구현 시에도 같은 위험도 분류를 적용합니다.

구체적인 생략·확대 조건은 [개발 규칙](DEVELOPMENT.md)을 따릅니다.

## 유지해야 할 실제 한계

현재 가드레일은 응용 프로그램 정책이며 OS 샌드박스가 아닙니다. 다른 프로세스가 검증 직후 파일시스템을 바꾸는 경쟁 조건을 완전히 막지 못합니다. `.jarvis-stop`은 도구 호출을 거부합니다. 파일 작업은 단계 사이에서, 관리 런처 서비스는 감시 스레드에서 추가 확인하지만 모든 실행을 즉시 종료하는 OS 중단기는 아닙니다. 예산은 작업별이 아닌 프로세스 단위 10분 시간창과 일일 상한이며 여러 서버 프로세스의 합계를 제한하지 않습니다. 검색 인덱스에는 암호화되지 않은 원문 사본이 저장됩니다. 상세 운용 한계는 각 사용 안내를 따릅니다.
