# J.A.R.V.I.S. 전체 실행 계획

갱신: 2026-10-25 (Asia/Seoul). 상태: **완료 근거 갱신 / 일부 실제 경로 검증 / 전체 무인 운영 미검증**.
이 문서가 실행 우선순위의 단일 기준이다. Phase·W·P·H는 아래 대응표로 추적한다. [이전 세부 명세](archive/plan-before-restructure-2026-10-23.md)와 [PR #12 제안](https://github.com/coddddin/jarvis-mcp/pull/12)은 참조이며, 기존 보안·호환성 조건을 유지한다. 충돌하는 이전 실행 순서는 본 문서로 대체한다. 작업별 담당·진행·증거는 [Board](guides/board.md)에만 기록한다.

## 1. 목표와 최적화 기준

사용자가 한 대화창에서 요청하면 자비스가 필요한 맥락을 찾아 범위 내에서 실행·검증·보고하고, 중단 후에도 안전하게 이어가는 개인 비서다. PC 제어·개발·개인 지식·메일/일정 브리핑을 유지하며 모바일·음성은 같은 작업 체계의 접점으로 확장한다.

우선순위는 안전/정확성 → 작업 완료율과 사용자 개입 감소 → 완료 시간·사용량·유지보수 비용이다. 토큰만 줄이려고 검증·출처·권한 확인을 생략하지 않는다. 새 고정비 0원 우선. 최적화 효과는 구현량이나 도구 수로 평가하지 않는다.

| 측정 | 기록 및 판단 |
|---|---|
| 결과 품질 | 동일 유형 작업의 성공/실패·검증 통과·재작업을 모두 기록. 성공한 작업만 골라 비교하지 않음 |
| 사용자 부담 | 승인에 필요한 개입과 오류 복구/재설명 개입을 분리. 안전 승인 감소를 목표로 삼지 않음 |
| 시간 | 접수부터 검증까지 시간, 실행 시간과 사람/한도 대기 시간을 분리 |
| 사용량 | 입력·출력·캐시·재시도·요약·하위 실행, measured/partial/unknown, 구독 한도와 API 추정 비용 분리 |
| 유지보수 | 공통 로직 중복, 새 의존성/서비스, 장애 복구 단계, 사용 빈도 대비 관리 부담 |

동일 버전의 대표 합성 작업으로 변경 전후를 비교하고 표본 수·환경·누락을 공개한다. 실제 사용 표본으로 보완하되 소표본에서 절감률/자동 배정 효과를 일반화하지 않는다. 품질·보안이 나빠지면 사용량 절감만으로 채택하지 않는다.

## 3. 공통 구조와 책임

| 계층 | 책임 / 재사용 | 금지할 중복 |
|---|---|---|
| 접점 | HUD·GitHub·향후 Telegram이 출처와 인증 근거를 보존해 요청/결과 전달 | 채널별 별도 작업 큐·배정 엔진·승인 해석기 |
| 작업 관리 | Board는 업무/담당/인수인계 기준, 기존 TaskStore·실행 장부는 실행 상태. task/run/parent 연결 | 같은 상태를 여러 DB에서 독립 수정, 두 번째 Board |
| 판단 | 기존 lead_planner가 범위·의존성·담당 제안. 일반 작업은 담당 1명 | 모든 요청을 모델로 재분류, 전 직원 상시 토론 |
| 실행 | Dispatcher가 깨우기/중복/대기 관리, worker_adapters가 직원 호출, HybridTeam은 필요한 작업 내부 분담 | 새 Dispatcher/새 에이전트 프레임워크, 계층 분할로 예산 우회 |
| 통제 | 기존 guardrails·roster·예약 정책을 공통 계약으로 연결. 각 실제 실행 경계에서 권한·중단·예산 재검증 | 접점에서 한 번 확인한 권한만 믿기, 문서/메시지를 승인으로 취급 |
| 기능 | 기존 features/tools·등록 workflow·웹·Google·파일·분석 기능 사용 | 기능마다 새 인증/재시도/보고 체계 |

이는 목표 계약이며 일괄 재작성 지시가 아니다. 기존 모듈에 작은 연결부를 추가하고 중복이 실제 확인된 부분만 정리한다. DB를 하나로 합치지 않으며 기존 MCP 이름·parse_usage 호출·저장 데이터 호환을 유지한다.

| 데이터 | 기준 원본 | 다른 위치의 용도 |
|---|---|---|
| 코드·설계 변경 | Git의 커밋/PR | Board에는 SHA·검증 참조 |
| 작업 담당·결과 | Board | 채널/HUD는 조회·표시, 실행 상태와 식별자 연결 |
| 실행·사용량·승인 | 해당 기존 트랜잭션 저장소 | 관련 ID로 연결, 승인 원본을 Markdown으로 복제하지 않음 |
| 대화 | 기존 ChatStore | 필요한 작업 요약만 선택 전달 |
| 임시 기억 | MemoryStore의 owner/project/revision 범위 | 영구 승인 지식이나 인증 ACL의 대체물 아님 |
| 확정 장기 지식 | 승인 근거·출처·버전을 갖춘 Obsidian 문서 | 색인은 재생성 가능한 파생물; 원문 사본 보안도 고려 |

## 4. 통합 로드맵 — J0~J5

각 축은 필요한 최소 단위부터 진행한다. 앞 축의 모든 부가 기능이 끝나야 다음 축을 시작하는 거대 순차 개발은 하지 않는다. 아래는 계획이며 자동 배정 목록이 아니다.

| 축 | 최소 산출물 | 착수 전제 / 완료 게이트 | 후속 범위 |
|---|---|---|---|
| J0 안전한 운영 기준 | 환경/PR/권한 점검, 단일 담당, 작업 ID, 복구 기준 | 미커밋 보존·기준 SHA 기록. 위험 쓰기 제한, 부적절한 신원/입력 거부. 기존 보안 회귀 유지 | 직원별 서버 신원 강제, 감사·자격 증명 수명주기·OS 격리 |
| J1 요청부터 검증까지 | 기존 Board→Dispatcher→직원→검증→보고 한 경로 | J0의 해당 경계 확인. 정상/중복/실패/중단·재시작 검증. 증거 없는 done 금지 | GitHub 오프라인 접수, 안전한 인수인계, 실행 상태 관찰 통합 |
| J2 비용·문맥 효율 | usage 정규화, 무변경 0호출, 반복 중단, 필요한 맥락만 전달 | J1 경로를 기준으로 계측. 누락≠0, 캐시 중복 합산 금지. 동일 작업 품질 유지 비교 | 부모/하위 합산, 원자적 공통 예약, 작업별 압축, 모델 배정 실험 |
| J3 지식 재사용 | 승인 문서의 제한 검색과 출처 반환 | J0 접근 경계·민감도 확인. 잘못된 프로젝트/초안 제외, 변경·철회 문서 처리 | 원본→초안→승인, 출처 의존성·복구, 반복 절차의 스킬 후보 |
| J4 접점·운영 편의 | 동일 작업 상태를 HUD/Telegram에 읽기 전용 제공 | J1의 신뢰 가능한 상태 + J0 인증. 시각·근거·unknown 표시, 재전송 중복 방지 | T2 중지→T3 접수→T4 대상 한정 승인, 이후 음성/화면 공유 |
| J5 효과 기반 확장 | 사용 빈도/효과가 확인된 루틴 하나씩 확장 | J1~J4 중 해당 전제와 실제 복원 검사. 신규 비용·권한은 별도 결정 | AST, 사이트별 읽기, 추가 문서 형식, 직원 추천, 상시 장비, 3D HUD |

### 실행 순서와 자원 배분

1. J0 점검 후 J1의 작은 정상 경로를 먼저 확인한다. J1 실패 원인에 필요한 J0 수정만 우선한다. 운영 실험 전 권한과 실행 상한을 확인하며 보안 미완성을 이유로 무제한 실행하지 않는다.
2. J2 사용량 정규화와 결정적 무변경 처리부터 연결한다. 전체 예산 시스템 완성을 기다려 단순 절약을 미루지 않는다. 공통 예약은 실행 경로 하나에서 시작해 확대한다.
3. J3의 기존 읽기 전용 검색은 지식 자동 생성 체계보다 먼저 활용한다. 출처/승인 유효성 검증을 생략하지 않는다. J4 상태 조회는 신뢰 가능한 상태가 마련되면 별도 작은 작업으로 진행할 수 있다.
4. 원격 쓰기/승인은 J0 인증과 J1 중복·복구 경계 이후, 자동 지식 쓰기는 J3 승인/충돌/복구 계약 이후다. 상시 운영 확대는 실제 복원과 중단 검증 이후다.
5. 기본 진행 중 구현 작업은 1개, 독립 검토는 필요할 때 1개. 사용자 또는 적용 규칙이 병렬 작업을 요청했고 경로·의존성·예산이 분리될 때만 확대한다. 수습 직원의 기존 제한을 유지한다.

### J2 상세 계약

- H-01A: 제공자별 input/output/cache 생성/cache 읽기, 누적/증분/불명확, measured/partial/unknown. bool·음수·손상 이벤트 거부, 관찰되지 않은 event ID를 만들어 중복 제거를 보장하지 않음. parse_usage 튜플과 과거 기록 호환.
- H-01B/C: root/parent/run별 합산과 호출 직전 원자적 예약. 중복·병렬·중단 후 복구 검증. 불명확한 사용은 확인 전 환불하지 않으며 CLI 내부의 절대 지출 상한을 보장한다고 말하지 않음.
- H-02: 등록 스크립트·검증된 인자·변경 해시 사용. 네트워크 실패는 무변경 아님. 중복 입력·재시작에서 부작용 반복 금지. 스크립트 내부 모델 호출도 계측.
- H-03/H-04: task ID별 관련 코드/지식/도구만 제공. 결정·기각 이유·금지 규칙·검증·미완료·원문 참조 보존. 요약 비용/캐시 영향 포함 비교. 단순 보고는 템플릿, 동일 오류·직원 응답 루프 중단. 유료 승격·자동 권한 확대 금지.

### 통합 AI 관찰 계획 — J1/J2/J4 (2026-10-26)

결정 `OBS-20261026`: 기존 ActivityStore·실행/사용량 장부·HUD를 먼저 연결하고, 외부 관찰 제품은 선택 가능한 조회 대상으로 평가한다. 사용자 승인 범위는 이 계획의 반영이며 설치·계정 연결·외부 전송·서비스 시작·유료 호출의 승인이 아니다. 아래 항목은 구현 완료 체크가 아닌 후속 작업 범위다.

1. **OBS-1 / J1-TRACE·J4-CASE — 작업별 통합 표시를 먼저 완성한다.** 기존 요청/실행/부모/단계/재시도 기록과 usage를 명시적인 ID 매핑으로 연결한다. 팀 Activity의 task_id는 request ID이며 Board/TaskStore ID와 같다고 추정하지 않는다. HUD에는 실행 흐름, 직원·모델, 시작/종료, 대기·실행 시간, 사용량 품질, 실패 단계와 관측 시각을 함께 표시한다. 첫 토큰 지연은 실제 첫 토큰 시각이 있을 때만 표시하며 총 실행시간으로 대체하지 않는다. CLI의 종료 시 usage 보고를 실시간 토큰 계측으로 포장하지 않는다. **완료 조건:** 정상/실패/재시도/재시작/늦은 이벤트/누락·잘림 표본, 해제 후 응답 차단, 미수집 unknown과 stale 표시, 자기보고·관찰·검증 구분을 확인한다. 기존 J1-TRACE/J4-CASE의 결손만 구현하며 별도 상태 원본을 만들지 않는다.
2. **OBS-2 / J2-COMPARE — 사용량과 비용의 의미를 분리한다.** API 제공자가 확인한 청구액, 모델 단가·버전·시각을 사용한 토큰 환산 추정액, 구독 사용 한도/초기화 시각을 별도 항목으로 둔다. 확인되지 않은 청구액은 null이며 구독 토큰 환산액을 실제 지출로 합산하지 않는다. 기존 measured/partial/unknown/missing·옛 미분류 계약, 캐시 비중복 계산, 부모·하위 합산 H-01B/C를 재사용한다. **완료 조건:** 중복 이벤트·캐시·측정 0·누락·가격 변경·미지원 모델에서 합계와 보고 범위가 보존되고, 출처 없는 금액/한도는 생성하지 않는다. 실행 중 잠정치와 확정 보고를 구분한다.
3. **OBS-3 / J1·J2 — Langfuse를 첫 외부 관찰 후보로 제한 평가한다.** OBS-1의 ID/출처 계약 이후 기존 기록을 Langfuse SDK 또는 OpenTelemetry로 내보내는 선택 어댑터 하나만 검토한다. 실행/승인/예산 원본은 기존 저장소에 남긴다. 기본 전송은 ID·시각·모델·상태·usage·고정 오류 코드이며 원문 프롬프트/응답/메일/비밀은 제외한다. bounded queue, 전송 기한, 중복 방지, 유실/실패 표시를 정의하고 exporter 오류로 모델을 다시 호출하거나 원래 작업을 실패시키지 않는다. **완료 조건:** 합성 trace로 계층·재시도·usage 대응, exporter 중단·재시작·중복·보존 상한, 비밀 제외, 실제 표시 지연을 확인한 뒤 유지비와 운영 부담을 판단한다. 셀프호스팅은 Web/Worker·Postgres·ClickHouse·Redis/Valkey·객체 저장소가 필요하므로 단일 PC에 즉시 상시 배치하지 않는다. 도입 시 버전을 고정하고 SDK/OTLP 수집 방식별 실시간성 조건을 다시 확인한다.
4. **OBS-4 / J2·J5 — API 게이트웨이는 직접 API 호출 확대 시에만 평가한다.** LiteLLM은 여러 제공자의 API 라우팅·비용·예산 통제가 실제로 필요할 때 후보로 둔다. Helicone은 API 관찰 중심 대안이며 둘을 동시에 추가하지 않는다. 기존 Ollama 리드와 구독형 Claude/Codex/Cursor CLI를 프록시로 자동 전환하지 않는다. 관찰은 프록시를 통과하거나 별도 계측한 범위에 한정된다. **완료 조건:** 지원 경로 하나에서 스트리밍·취소·timeout·중복·usage/가격 누락·DB 장애 시 예산 동작을 검증하고 기존 상한을 유지한다. 예산 DB와 가격 정보가 없는 구성을 비용 차단 보장으로 표현하지 않는다. 실계정 비용·인증 방식은 실행 전에 확인한다.

선정하지 않은 대안도 이유를 남긴다. Braintrust/Maxim은 평가 데이터·품질 비교 요구가 기존 J2-COMPARE를 넘어설 때 재검토하고, 초기부터 Langfuse와 중복 설치하지 않는다. AI Token Monitor류는 로컬 세션 로그 집계와 화면 구성을 참고하되 이름이 같은 제품을 혼동하지 않는다. 일부는 로그 기반 환산액, 일부는 계정 자격증명을 읽어 한도를 조회하므로 정확한 저장소·라이선스·데이터 접근 범위를 검토하기 전 코드 복사나 설치를 하지 않는다. 별도 앱의 숫자를 Jarvis 작업별 원본으로 그대로 가져오지 않는다.

**착수 순서:** J1-TRACE/J4-CASE의 OBS-1 결손 확인 → OBS-2의 기존 usage 연결 → 필요성이 확인된 OBS-3 합성 export 실험. OBS-4와 상용 평가 플랫폼은 후순위다. 각 단계는 기존 Board에 한 과업으로 claim하고 필요한 경우에만 실제 실험을 승인받는다. 계획 추가 자체는 자동 배정이나 설치 신호가 아니다.

### J3~J5 확장 경계

- 지식: 원본 불변·출처 URL/ID/수집시각/해시, 초안과 승인 분리. 생성자 자기 승인 거부, 원본 변경/철회가 파생 문서에 반영. frontmatter 호환 및 Vault 쓰기/외부 모델 전송 범위를 확정한 후 구현. 자동 스킬 채택·삭제·비활성화 금지.
- Telegram: 허용 user/chat ID·토큰 보관·update ID 중복 방지·빈도/길이 제한·그룹 봇 응답 기본 차단. T2는 접수와 실제 중단 구분/소유 프로세스 식별. T4는 작업/행동/대상/변경 해시/만료/일회성 nonce 결합. 일반 긍정 답변을 임의 승인으로 해석하지 않음.
- 복구: SQLite 일관 스냅샷, 큐/승인/예산/outbox 재검증, 완료 승인 재사용 및 불명확한 외부 부작용 재실행 금지. 합성 Vault 복원 성공을 실제 R2/Vault 운영 복원으로 일반화하지 않음.
- 기능 확장: 공개 수집/학교 공지/배송 등 루틴 하나씩. 로그인은 사용자 직접, 허용 출처와 접근 제어 준수. AST는 Git 검색이 부족한 증거가 있을 때 Python부터, 동적 참조 누락 시 보수적 테스트. 새 벡터 DB/서버/다중언어 분석은 효과 확인 후 판단.
- 기존 파일 정리·스냅샷·다운로드·코드 적용은 미리보기→대상/해시/충돌 재검증→허용된 적용→검증/복구 흐름 유지. 새 쓰기 범위나 삭제 권한을 계획으로 부여하지 않음.

## 7. 한 문장 재개 계약

사용자가 집 PC의 기존 자비스 개발 세션에 “최신화하고 작업시작해”라고 요청하면 다음을 적용한다. main의 기존 파일이나 꺼진 PC에 자동 전달됐다고 주장하지 않는다. 발견 경로는 최신 [PR #13](https://github.com/coddddin/jarvis-mcp/pull/13) 설명과 이 문서다.

1. git status/worktree, 실제 프로세스, Board inbox/list, 최신 PR head/base를 확인한다. 기존 미커밋·claim은 보존하고 stash/reset/공유 checkout pull/자동 채택하지 않는다. fetch는 병합·배포가 아니다.
2. 기존 `RESUME-H01-USAGE-V1` 작업이 활성이라면 중단·재배정하지 않는다. 담당과 새 계획 관계를 기록한다. 없거나 완료되었으면 `J1-ACCEPTANCE-V1`을 조회·재사용하여 단일 담당을 확정한다. 제목만으로 원자적 중복 방지가 보장되는 것은 아니므로 동시 생성 시 담당 확인 전 실행하지 않는다.
3. 범위가 충돌하지 않는 별도 branch/worktree와 기준 SHA를 기록한다. 실제 명부 확인 후 재개 task ID·담당·범위·PR 링크·금지사항을 Board로 전파한다. 단순 공지는 `*`, 실제 직원 배정은 필요한 담당만. 성공 메시지 ID와 읽음/착수를 구분한다.
4. Board가 없으면 상태·GitHub·명세 읽기와 독립 준비만 진행한다. 공동 수정은 연결 복구 또는 사용자 지정 대안 전 보류. DB 직접 편집·가짜 Board·전달 성공 허위 보고 금지.
5. 실제 직원 호출 전 기존 계정/권한/한도를 확인한다. 스케줄러 설치·교체와 무인 실행의 기존 승인 차단은 우회하지 않는다. 불가하면 합성 검증과 필요한 사용자 조치만 보고한다.

### 첫 작업 J1-ACCEPTANCE-V1

- 목적: 현재 시스템의 접수→담당 확보→실행→검증→보고를 좁은 경로에서 확인하고, 발견된 연결 오류만 고친다. 새 리드 엔진을 만들지 않는다.
- 먼저 읽기: Board/dispatcher/hybrid-team 안내와 관련 테스트, `jarvis/agents/lead_planner.py`, `dispatch_policy.py`, `worker_adapters.py`, `jarvis/cli/dispatch.py`. 실제 실행 저장소 계약은 호출 경로에 따라 확인한다.
- 입력: 공개 합성 자료를 사용하는 작은 읽기 전용 작업. 합성 어댑터로 먼저 검증하며 실제 직원 테스트는 허용된 수동 경로/기존 상한 안에서만 수행한다. main/실Vault/인증/스케줄러 변경 제외.
- 검증: 정상 완료, 동일 입력 재수신, 동시 담당 경쟁, 실패/시간초과, 중단 후 재개. 실행 성공과 증거 검증을 분리하고 외부 부작용이 불명확하면 재실행하지 않는다.
- 계획 후보 경계: 이 PLAN에는 미완료 체크박스를 두지 않는다. 따라서 기존 체크박스 수집기는 이 문서에서 후보를 만들지 않는다. 이는 의도된 자동 배정 보류이며 코드 변경 없이 새 J-ID 파싱이 구현됐다고 말하지 않는다. 향후 명시적 후보 ID/상태/범위→검증→Board 승인된 배정으로 연결하고, 보관 문서는 스캔하지 않는 회귀를 추가한다. 기존 Board 작업은 취소하지 않는다.
- 기본 수정 범위: 관련 테스트와 확인된 최소 연결부. 변경 전 Board 경로 claim, 공용 계약/마이그레이션은 범위 재확인. 이미 해결된 항목은 증거만 남긴다.
- 완료: 기준 SHA·변경 파일·명령/종료 코드·모의/실제 구분·미검증·다음 작업을 Board에 기록하고 Draft PR. 코드/권한/공유 계약 변경은 독립 검토. 단순 문서는 문서 검사와 diff 확인. 실패를 skip/가짜 성공으로 숨기지 않는다.
- 후속: J2 H-01A 정규화와 H-02 무변경 루틴을 작은 작업으로 선택. 검증되지 않은 실제 실행을 완료라고 표시하지 않는다.

## 8. PR·검증·권한 운영

- #8→#10→#11→#13은 main에 통합된 기반 의존성이다. PR 번호순 자동 개발/병합이 아니다. #9와 #3~#5는 별도 범위이며 상태/API/이벤트 구현은 검토 후 재사용한다. #12는 설계 참조, 중복 구현하지 않는다.

- 실제 Board 연결 없는 이 계획 세션은 원격 문서 준비만 수행한다. Board 발송·데스크톱 배포·직원 착수를 주장하지 않는다.
- 사용자 승인 없는 main 병합·파일 삭제·유료 서비스 활성화·예약 설치/교체 금지. 기존 데스크톱 작업 보호. 계획은 권한 부여나 실행 신호가 아니다.
- 응용 가드레일은 OS 샌드박스가 아니다. stop 표시는 모든 프로세스의 즉시 종료를 보장하지 않는다. 인덱스는 평문 원문 사본을 포함할 수 있다. 명부 ID/task ID는 인증이 아니다. 구독 CLI의 내부 호출을 모두 관찰·차단할 수 있다고 가정하지 않는다.
