- 결정일: 2026-10-28. 근거: 사용자 직접 결정(이 날 대화의 선택 응답). 2026-10-27 사용자 정책 12번 "다른 프로그램이 자원을 사용하면 그 프로그램을 우선하고 자비스 작업은 부하에 맞춰 줄인다"를 구체화한다.

## 배경

이 PC: GPU RTX 4070 Ti SUPER 16GB, RAM 31GB, CPU Ryzen 7 9800X3D 8코어 16스레드.

2026-10-28 `hud --voice` 실행 중 측정한 값:

- GPU 16GB 중 15.6GB가 쓰였다. 자비스 몫은 약 12.8GB다.
  - 채팅 모델 llama-server: 6.7GB
  - CosyVoice: 3.8GB
  - 받아쓰기: 2.3GB
- RAM은 사용 가능량이 7.4GB뿐이었다. CosyVoice 프로세스가 GPU와 별도로 RAM 4.2GB를 썼다.
- 문제: 모든 모델이 쓰지 않을 때도 올라가 있다.
  - 음성 모델은 HUD가 끝날 때까지 남는다.
  - 채팅 모델은 마지막 요청 뒤 30분 남는다.
- 위험: 다른 프로그램이 GPU를 더 쓰면 Windows가 넘치는 몫을 RAM으로 밀어낸다. 그러면 꺼지지 않고 양쪽이 모두 느려진다.

## 결정

1. **다른 프로그램 우선, 자동 양보.**
   - GPU 여유가 기준 아래로 내려가면 자비스가 스스로 아래 순서대로 줄인다.
     1. 받아쓰기를 CPU로 옮긴다.
     2. CosyVoice를 절전한다. 그동안 읽기는 Windows 음성 Heami가 한다.
     3. 채팅 모델을 절전한다.
   - 여유가 돌아오면 같은 순서를 거꾸로 밟아 되돌린다.
   - 지금 상태와 이유를 트레이와 화면에 표시한다.
   - 사용자는 트레이에서 직접 비울 수도 있다.
2. **하드웨어별 역할.** GPU에 고정 상한을 두지 않고, 각 장치가 잘하는 일을 맡긴다.
   - GPU: 지연에 민감하고 메모리 대역폭이 결정하는 일. 채팅 답변 생성과 CosyVoice 음성 합성.
   - CPU: 음성 감지, 숫자 읽기 변환, 색인·검색, 백그라운드 작업. GPU가 부족할 때는 받아쓰기도 맡는다. 평소 받아쓰기를 어느 장치에서 할지는 측정 후 정한다.
   - RAM: 절전 중인 모델을 보관하는 대기 공간이다. 디스크에서 다시 읽는 것보다 빨리 GPU로 되돌린다.
   - SSD: 꺼진 모델을 둔다.
3. **모델은 활성 → 절전 → 꺼짐의 세 단계로 둔다.**
   - 활성: GPU에 올라가 바로 답한다.
   - 절전: 일정 시간 입력이 없으면 RAM으로 내린다.
     - 받아쓰기: faster-whisper `WhisperModel` 안의 CTranslate2 객체(`WhisperModel.model`)가 `unload_model(to_cpu=True)`를 지원한다. 이렇게 RAM에 보관한 모델은 CPU에서 받아 적지 못한다. `load_model()`로 GPU에 되돌려야 쓸 수 있다.
     - 결정 1의 "받아쓰기를 CPU로"는 이 절전과 다르다. CPU용 모델(small, int8)을 따로 올리는 것이라 RAM이 더 든다. CosyVoice는 모델을 CPU 메모리로 옮겨 구현한다. Ollama에는 RAM 보관 기능이 없다. 그래서 내리면 GPU에서 완전히 빠지고, 모델 파일이 Windows 파일 캐시에 남아 있으면 더 빨리 다시 올라온다. 남아 있다는 보장은 없다.
   - 꺼짐: 더 오래 입력이 없거나 RAM이 부족하면 완전히 내린다.
   - 깨우기: 사용자가 입력을 시작하는 순간 미리 올리기 시작한다. 예: Space를 누르는 순간, 입력창에 쓰기 시작하는 순간. 받아쓰기는 사용자가 말하는 동안 올린다. 목소리는 받아쓰기와 답변 생성 동안 올린다. 기다리는 시간이 말하고 생각하는 시간 뒤에 숨도록 하는 것이 목표다.
4. **목소리는 사용자가 고른 CosyVoice JARVIS 목소리를 유지한다.** 가벼운 방식(fp16)으로 GPU와 RAM을 줄일 수 있는지 측정한다. 음질이 떨어지면 지금 방식을 유지한다.
   - 주의: 이 사본에서 CosyVoice3 생성자의 `fp16` 옵션은 `torch.cuda.amp.autocast`만 켠다. 가중치는 fp32로 올라가서, 가중치 몫의 GPU 메모리와 RAM은 거의 줄지 않을 수 있다. 줄어드는 것은 중간 계산 메모리 정도다.
   - 가중치를 줄이려면 별도로 반정밀도 변환을 해야 한다. 변환 뒤에는 음질을 확인한다.
5. **측정 없이 수치를 확정하지 않는다.** 측정 기록과 함께 이 문서에서 바꾼다.

### 측정값 (2026-10-28, 이 PC)

측정 방법: 구성마다 별도 프로세스에서 쟀다. GPU는 nvidia-smi로 본 장치 전체 사용량의 증가분이다. 받아쓰기는 Heami로 만든 13.3초 한국어 고정 클립을 썼다. 원본 기록은 Board 과업 8be58606의 측정 노트다.

|---|---|---|---|---|---|
| 받아쓰기 turbo | CUDA float16 | +2.2GB | +0.2GB | 0.15초 (RTF 0.011) | CER 0.02 |
| 받아쓰기 turbo | **CUDA int8_float16 (채택)** | +1.2GB | +0.2GB | 0.15초 | CER 0.02 (같은 글자) |

### 정한 값

RAM 절전 보관은 음성 모델에 쓰지 않는다. 측정해 보니 RAM 비용(1.4~7.5GB)이 크고, 완전히 내렸다가 다시 올리는 기다림은 사용자가 말하는 시간 뒤에 숨는다.

| 항목 | 값 |
|---|---|
| 받아쓰기 꺼짐 | 입력 없이 5분 뒤 완전히 내림. 마이크를 여는 순간 다시 올림(1~2초) |
| CosyVoice 꺼짐 | 입력 없이 30분 뒤 작업자 종료. 마이크를 열거나 답을 읽어야 할 때 다시 시작하고, 준비될 때까지 Heami가 읽음 |
| 유휴 확인 주기 | 15초. 듣기·받아쓰기·읽기 중에는 내리지 않음 |
| 채팅 모델 | 유지 5분, 입력을 시작하면 미리 올림(별도 PR) |
| 자동 양보 시작 | 임시값: GPU 여유 2GB 미만이 10초 이상 계속될 때 |
| 되돌리기 | 임시값: GPU 여유 4GB 이상이 30초 이상 계속될 때 |

## 결과와 남은 문제

- 오래 쉬었다가 처음 요청하면 기다림이 생긴다. 미리 올리기로 줄이되, 실제 시간은 단계마다 잰다(절전에서, 꺼짐에서).
- 되돌릴 수 있는 CosyVoice 절전에는 새 상태가 필요하다. 지금의 고장 대체 경로(#69, 음성 엔진이 실패하면 닫고 HUD가 끝날 때까지 Heami로 고정)는 되돌아오지 않으므로 이 용도로 쓰지 않는다.
- RAM도 넉넉하지 않다. 세 모델을 모두 절전으로 RAM에 두면 사용 가능량을 넘을 수 있다. 그래서 절전 보관은 RAM 여유가 있을 때만 하고, 모자라면 꺼짐으로 보낸다.
- Ollama 설정(유지 시간, 문맥 저장 압축 `OLLAMA_KV_CACHE_TYPE=q8_0`)은 Ollama 관리자와 조율한 뒤 바꾼다. 공식 FAQ 기준으로 q8_0은 문맥 저장 공간을 약 절반으로 줄이고, 정밀도 손실은 매우 작다.
- 양보 기준인 GPU 여유는 Windows에서 프로세스별로 정확히 재기 어렵다. 프로그램끼리 함께 쓰는 화면 메모리가 프로세스마다 겹쳐 잡히기 때문이다. 그래서 장치 전체의 여유량(nvidia-smi 또는 NVML)을 기준으로 삼는다.
