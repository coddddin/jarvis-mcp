> 2026-10-17 사용자 제공 원안 보관본입니다. 원안의 Phase 2 “완료”와 agents/ 표시는 구현 증거가 아닙니다. 현재는 실용 도구가 미구현이고 agents/도 없습니다. 실제 상태와 진행 기준은 [통합 계획](PLAN.md)을 따릅니다. 요청한 경로에 보관하며 다른 버전 원안과 함께 문서 안내에서 관리합니다.

## 1. 프로젝트 비전 및 목표

- 최종 목표: 사용자의 PC 환경을 수족처럼 부리며, 지식(세컨드 브레인)과 음성·시각 인터페이스를 통해 실시간으로 상호작용하는 개인용 슈퍼 AI 에이전트 시스템 구축.
- 핵심 가치:
  - 다중 에이전트 자율 협업 (기획 ➔ 작성 ➔ 테스트 ➔ 수정 자동화)
  - 극강의 실용성 (일상 업무 및 개발 귀찮음 제로화)
  - 안전성 및 토큰 최적화 (화이트리스트 가드레일, 예산 제한, 툴별 독립 플러그인 구조)

## 2. 프로젝트 아키텍처 및 멀티 에이전트 구조

### 2.1 다중 에이전트 오케스트레이션 (Multi-Agent Interaction)

사용자는 통합 창에 요구사항만 툭 던져놓으면, 내부의 전문 에이전트들이 서로 대화하고 부탁하며 자율 검수 루프를 수행합니다.

- **Planner-Agent (기획자):** 사용자 요구사항 분석, 작업 분할, 전체 계획서 수립.
- **Coder-Agent (개발자):** 가드레일 규칙을 준수하며 실제 작동 가능한 코드 작성.
- **QA/Tester-Agent (검수자):** 셸 환경에서 코드를 직접 테스트하고, 에러 발생 시 Coder에게 원인 피드백 및 재작성 요청.
- **Orchestrator (중앙 통제소):** 에이전트 간 대화 핸드오프 및 사용자 통합 창에 최종 결과 보고.

### 2.2 디렉토리 구조

- `server.py`: 메인 실행 파일
- `guardrails.py`: 보안 가드레일
- `agents/`: 멀티 에이전트 페르소나 및 통제소
- `tools/`: 독립 플러그인 툴 모음 (`file_organizer_tool.py`, `debug_assistant_tool.py`, `workflow_launcher_tool.py`, `snapshot_tool.py` 등)

## 4. 2026-10-17 추가 합의 — Phase 2.5 세부 제어

위 원안에 대한 사용자 요청 보완입니다. 현재 구현 상태는 여전히 미착수이며 자세한 완료 조건은 [통합 계획](PLAN.md)에 유지합니다.

### Phase 2.5 — 다중 에이전트 협업 오케스트레이션 구축

1. **에이전트 기억 장치 (Memory Store):** 단기 작업 대화·상태와 장기 사용자 선호·경로·검증된 오류 해결 이력을 분리해 로컬 JSON/DB 및 필요 시 벡터 저장소에 보관합니다. 출처·보존 기간·조회·정정·삭제와 비밀정보 제외를 설계하며 기억으로 현재 권한을 확대하지 않습니다.
2. **무한 루프 방지 (Circuit Breaker):** 최초 시도와 별도로 Coder 수정→QA 재검수는 최대 3회입니다. 세 번째 수정도 실패하면 자동 루프를 중단하고 사용자 피드백을 요청합니다. 호출·토큰·비용·시간 한도는 모든 역할과 재시도가 공유하며 더 먼저 한도에 도달하면 중단합니다. 작업 재개·에이전트 교체로 카운터를 자동 초기화하지 않습니다.
3. **실시간 이벤트 버스 (Async Event Bus & WebSocket):** 에이전트 작업 상태·사용자용 메시지·도구 요약·검수 결과를 정제된 이벤트로 전달합니다. 인증·순번·유한 큐·역압·재연결을 포함하고 로컬 일반 부하에서 발행→HUD 표시 p95 100ms 이하를 검증 목표로 둡니다. 내부 사고 과정·비밀정보를 전송하지 않습니다. 버스·프로토콜은 Phase 2.5, 실제 HUD 표시 통합은 Phase 3에서 검증합니다.

## 5. 2026-10-17 추가 합의 — 속도 및 토큰 최적화

- **Fast-Pass:** 주석·단순 텍스트·동작에 영향 없는 UI 변경은 별도 QA를 생략하고 최소 확인 후 완료합니다. 실행 권한·파일 변경·인증·업무 로직에 영향을 주는 변경은 위험도에 맞는 검증을 유지합니다.
- **Smoke Test:** 변경 모듈 단독 검증을 약 1초 목표로 먼저 실행하고, 영향·실패 근거가 있을 때 관련 회귀·통합 검사로 확대합니다. 매번 전체 테스트를 반복하지 않습니다.
- **Pydantic 타입 계약:** 새 입력·출력·이벤트 등에 모델 검증을 점진 적용합니다. Pydantic은 런타임 데이터 검증이며 작성 시 정적 타입 검사를 대체하지 않습니다. “오류 90% 사전 차단”은 제안 목표로 기록하고 측정 전 보장하지 않습니다.

현재 개발 절차와 적용 상태는 [통합 계획](PLAN.md) 및 [개발 규칙](DEVELOPMENT.md)을 따릅니다. 이번 문서 반영으로 자동 QA 라우팅이나 타입 검사기가 구현된 것은 아닙니다.
